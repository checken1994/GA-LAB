# R44 Semantic Correctness và Promotion Decision

**Scope:** sáu persisted evolution lessons trong `data/kb_evolve.sqlite` có `bug_type=BareExceptPass`.  
**PC evidence:** semantic audit chạy trên `C:\Users\check\Downloads\scp`.  
**Current decision:** `REJECT` cho cả sáu; `policy_promotion=false`.

## 1. Problem statement

Sáu lesson có `fix_verified=1` và `success_rate=1.0`, nhưng những fields này là metadata do SCP ghi. Câu hỏi cần kiểm chứng là liệu từng patch có giữ đúng semantics hay không, liệu có evidence độc lập ngoài chính SCP hay không, và liệu candidate có thể tự động đi vào active policy hay không.

## 2. Why chain

**Tại sao `success_rate=1.0` chưa đủ?** Vì DB không có original source snapshot, patched source, expected source hash hoặc semantic test result cho từng lesson.

**Tại sao phải kiểm tra đúng line?** Vì một `BareExceptPass` claim chỉ hợp lệ nếu AST tại file/line có `ExceptHandler.type is None` và body duy nhất là `pass`.

**Tại sao cần external evidence?** Vì cùng một scanner/runtime lineage có thể lặp lại cùng một blind spot; consensus nội bộ không phải independent truth.

**Tại sao không promote khi test parser pass?** Vì parsing chỉ chứng minh syntax. Nó không chứng minh exception control-flow, cancellation, shutdown hoặc caller intent được bảo toàn.

## 4. What has actually been proven

The following bounded statements are proven by independent documentation plus runtime evidence:

1. The transformation `except: pass` to `except Exception: pass` parses when generated by the candidate rule.
2. For an ordinary `Exception` such as `ValueError`, the tested handler outcome agrees.
3. The transformation is **not universally semantic-equivalent**: the real PC test observes `bare=caught` and `typed=propagated` for `KeyboardInterrupt`, `SystemExit` and `GeneratorExit`.
4. The six persisted lesson locations are currently typed `except Exception: pass`, so their persisted `BareExceptPass` classification is contradicted by the current source at the recorded lines.
5. Subject-level evidence for the generic semantic contract cannot be reassigned to the six lesson IDs. The ledger correctly returns `eligible=false` for each lesson ID because no evidence record names those subjects.

This is stronger and more honest than claiming that all six patches are semantically proven. The current evidence proves **promotion must be blocked**, not that every historical patch is wrong in every possible context.

## 6. Next step

The next step is **snapshot recovery**, not promotion. For each lesson, recover an exact pre-fix source snapshot from one of these independent locations: a Git commit/object, release backup, append-only patch log, or immutable artifact backup. The recovered artifact must produce a SHA-256 matching the lesson's expected source hash. If no such artifact exists, the lesson cannot be promoted; it may only remain quarantined as an unverified historical claim.

After recovery, run a per-lesson semantic matrix covering ordinary `Exception`, `KeyboardInterrupt`, `SystemExit`, `GeneratorExit`, cancellation/timeout behavior, caller return values and side effects. A reviewer or independent test lineage must attach the outcome to the lesson ID. Only then can R43 policy materialization be invoked in staging; it must produce a candidate, run A/B consumer behavior, create a backup, promote atomically, run reality tests, and permit rollback. No unresolved or metadata-only lesson may bypass this sequence.
